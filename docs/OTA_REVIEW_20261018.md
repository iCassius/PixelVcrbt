2026-10-18。依据当前工作区源码、[实机记录](DEVICE_TEST_20261018.md)及 Android 官方文档。用户已反馈目前测试正常。本轮只复盘和记录，不改代码、不重新安装或操作手机。

后续进展：下述诊断及音频端点两项已完成本地实现和验证，详见 [本轮改进记录](OTA_HARDENING_20261018.md)；新的候选尚未进行实机验收。下文保留复盘时的现状描述。

## 本次问题

1. 原正式版三处按电话版本号拒绝运行。电话更新后，探测接收器仍能注册，业务 Hook 却在安装前返回，造成“入口存在但业务未安装”。根因是把版本号当作功能特征，不是已经证明新版电话破坏了视频接口。
2. 首个重构候选又把应用层 VideoCall 的单参数请求误写成底层 Binder 的双参数形式。无通话时的编译、入口检测与策略测试未覆盖该对象，直到真实拨号才暴露异常。现已修正，并增加真实 Android SDK 签名测试。以后必须检查实际交互层级，不能把相似名称的接口混用。
3. 当前已按类、继承、完整签名和运行对象判断；必要 Hook 安装失败撤回，可选音频保护独立决定，状态回复带运行代码标识和有效期。复测确认视频画面更新、听筒路由恢复及挂断清理。仍未完成接通后的完整业务回归。

## 系统升级可能影响什么

以下是从依赖关系推断的风险，不是声称这些变化已经发生。

| 变化位置 | 可能表现 | 应如何适配 |
| --- | --- | --- |
| 内核、ART、Root/LSPosed 运行环境 | 模块根本没有进入电话进程 | 先区分电话未启动与框架未注入；检查新系统对应的框架运行情况。应用内改方法名不能修复框架注入失败；不扩大作用域 |
| 电话 APK 的入口类、通话 Activity 或布局 | 必要特征缺失，或已加载但无法识别远端视图 | 为新结构增加有证据的特征契约。Service 可用 Manifest 声明、BIND_INCALL_SERVICE、继承和完整回调共同确定，候选必须唯一；Activity 不能仅凭继承关系随意选择。远端视图同样要证明角色和唯一性 |
| Telecom/具体 VideoCall 实现与音频端点 | 动态视频检查失败、Surface 被替换、音频恢复失败 | 核对公开 API 与实际实现的方法描述符；分别处理对象替换和会话代际。音频优先用系统提供的 CallEndpoint，旧方法只作经过检查的后备 |
| 权限、隐藏接口及广播规则 | 配置读取失败、属性读不到、状态页无回复或 IMS 不可读 | 分别报告读取错误、权限拒绝和超时；检查电话进程实际权限及 target SDK 条件。优先采用公开 API，无法读取不能显示成用户主动关闭 |
| IMS、基带、vendor 或运营商配置 | IMS 可注册，但没有早期视频、回调顺序不同，或四项配置已不适用 | 核对实际起呼意图、状态时序、provider 与有效配置，再定位到相应层。字段同名且同为 Boolean 仍不证明语义一致；不能盲目重写 vendor 键或强制改为视频呼出 |

系统升级和电话应用更新是两个独立变量，也可能同时发生。诊断应记录两者、框架运行信息及模块源码标识；这些是追溯信息，不作为版本白名单。

Android 官方说明非 SDK 接口限制会随平台调整，反射访问可能失败；当前 `ActivityThread`、`SystemProperties`、`ServiceManager` 和内部配置 Binder 都需要单独关注。[非 SDK 接口限制](https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces)

音频有一个明确的维护方向：当前主动恢复仍调用 `setAudioRoute()`，该方法在 API 34 已弃用，官方推荐 `requestCallEndpointChange()`；弃用不等于现在已失效。端点必须来自系统公布的列表，不能自行构造。[InCallService 文档](https://developer.android.com/reference/android/telecom/InCallService#requestCallEndpointChange(android.telecom.CallEndpoint,java.util.concurrent.Executor,android.os.OutcomeReceiver))

## 下一轮优先补什么

1. **先补业务失败诊断**：`enabled()` 和音频开关反射读取异常目前返回 false，缺少明确原因；`providerReady` 失败和找不到远端视图也尚未完整呈现为结构化结果。详情应保留具体步骤、原因和发生时间，区分本次实时状态与历史失败，避免一个后续 idle 覆盖关键原因。主页面继续保持简洁。
2. **再做音频端点适配**：公开 CallEndpoint 路径优先，确认端点实际切换；用户手动选择后不再自动改回，缺少必要能力则停止自动恢复。音频迁移单独回归，不夹带渲染改动。
3. **再扩充入口与布局契约**：当前仍固定两个入口类名及 `videocall_video_remote` 资源名，尚不是任意电话结构都能识别。只在发现新结构并取得明确证据后增加适配器，选择依据始终是特征；不按系统/电话版本分配一个“看起来相近”的适配器。
4. **保持分层验证**：SDK 签名测试、错误注入、APK 静态核验、真实运行与业务体验分别记录。接口存在不证明行为相同，IMS 注册不证明彩铃或真正视频通话正常。

## 每次升级后的最小检查

- 升级前保存可用模块包、签名和简短的配置/运行摘要，不保存联系人或原始音视频到公开材料。原 3.1.1 正式包仍有限定电话版本的旧逻辑，不能把它当作新电话上的已验证回退包；应保留本轮实际可用的同签名构建。
- 升级后先正常打开电话，确认实时回复来自当前模块代码、必要 Hook 已安装、配置可读及 IMS 状态。电话进程被系统回收时“未连接”是连接状态，不等于开关关闭。
- 经授权用联系人完成一次未接通彩铃，再补接通语音、原生主动视频、听筒/扬声器/蓝牙选择和结束后清理。系统大版本升级还需检查锁屏/后台/旋转、SIM 或网络切换后的行为。紧急排除用离线用例检查，不拨真实紧急号码。
- 只有具体功能失败时才停用该功能并收集原因，保留原生通话。不能把关闭 ViLTE、扩大 LSPosed 作用域或重写所有配置作为通用修复。

当前机制消除了“版本号变了就拒绝运行”的问题，但不能保证未来所有系统变化都无需适配。正确目标是：实际依赖仍成立就继续工作；不成立时明确说明哪一步失败，并保留原生电话能力。
